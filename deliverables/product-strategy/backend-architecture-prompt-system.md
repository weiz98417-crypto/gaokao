# 高考志愿填报APP · 后端架构设计提示词体系

> **用途**：本文件是驱动 AI 完成后端架构设计的完整提示词工程手册。你可以把「主提示词」直接投喂给大模型，也可以按阶段拆分使用；所有专项提示词用于深度补充特定领域。
>
> **目标**：为「考生成绩/意向采集 + 智能推荐引擎」MVP 设计一套**高性能、高并发、高可用**的后端架构，支撑出分日集中爆发的流量洪峰。

---

## 一、使用指南

### 1.1 推荐用法
| 场景 | 使用方法 |
|------|----------|
| **一次性完整设计** | 复制「主提示词」+「项目上下文」+「输出模板」，要求模型一次性输出完整架构方案。 |
| **分阶段深度设计** | 按阶段 1→8 顺序依次执行，每轮基于上一轮输出继续细化。 |
| **专项补充** | 当主方案缺少安全/缓存/压测细节时，追加对应专项提示词。 |
| **多模型对比** | 用同一套主提示词让多个模型输出，再用「评估 Checklist」做交叉评审。 |

### 1.2 变量替换说明
提示词中出现的 `{{变量}}` 需要在使用前替换为实际值：
- `{{TARGET_QPS}}`：目标峰值 QPS（如 5000/10000/50000）
- `{{TARGET_PROVINCES}}`：本次覆盖省份（如 广东、河南、山东等 Top10）
- `{{BUDGET_LEVEL}}`：成本约束（如 严控/适中/充裕）
- `{{TEAM_SIZE}}`：后端团队人数（当前为 2 人）

## 二、项目上下文（复制到任何提示词前）

```text
【项目背景】
- 产品：高考志愿填报 APP，当前处于 MVP 阶段。
- 核心模块：考生成绩/意向采集与智能推荐引擎。
- 推荐算法：位次直查法为主，线差法校验，3 年加权（权重 0.4/0.35/0.25）。
- 用户交互：Wizard 5 步分步式为主入口，AI 对话式为辅入口。
- 偏好模型：院校/地域/专业三角权重 + 3 滑块 + 零偏好模式。
- MVP 覆盖：Top10 省（广东、河南、山东、江苏、四川、河北、湖南、安徽、湖北、浙江）。
- 时间线：核心开发 10 周（2026.7.14-9.22），长周期测试 2026.10-2027.5，出分日上线 2027.6.23-25。
- 团队：6 人（数据 1 + 后端 2 + 前端 2 + 产品 1），后端人力极其紧张。

【业务特征】
1. 流量高度集中：高考出分后 3-5 天内出现爆发式访问，其余时间流量平稳。
2. 计算密集：单次推荐需执行位次匹配、线差校验、多维度加权排序。
3. 数据热读冷写：院校/专业/历年分数线数据在考季前基本固化，出分后只读查询量巨大。
4. 地域隔离：用户只关心本省招生计划与分数线，天然可按省分片。
5. 结果敏感：推荐结果直接影响考生志愿，数据准确性要求 100%，延迟要求 <500ms（P95）。
6. 突发峰值不可预测：热门省份可能出现 10 倍以上日常流量。
```

## 三、主提示词（Master Prompt）

```text
你是一位资深后端架构师， specialize in 高并发、高可用、高性能系统设计。请基于以下项目上下文，为一款高考志愿填报 APP 设计完整后端架构方案。

{{粘贴项目上下文}}

【设计要求】
1. 架构目标：高性能（推荐接口 P95 < 500ms）、高并发（峰值 QPS ≥ {{TARGET_QPS}}）、高可用（SLA ≥ 99.9%，出分日不宕机）。
2. 团队约束：后端开发仅 2 人，必须优先选择成熟、易运维、少自研组件的方案。
3. 成本约束：{{BUDGET_LEVEL}}，需要明确说明关键成本项。
4. 覆盖范围：{{TARGET_PROVINCES}}。

【必须覆盖的内容】
A. 总体架构：架构模式、通信协议、部署形态、服务边界。
B. 服务拆分：按 MVP 核心模块拆分微服务/模块，说明每个服务的职责、数据 ownership、对外接口。
C. 数据架构：核心实体 ER 设计、关键表结构、索引策略、分片/分区方案、主从/读写分离策略。
D. 推荐引擎架构：位次直查 + 线差校验 + 加权排序的计算链路、缓存策略、预计算/实时计算权衡。
E. 缓存与性能：多级缓存（CDN/本地缓存/Redis/应用缓存）设计、缓存一致性、热点数据防护。
F. 高可用与容灾：多可用区部署、数据库主从切换、熔断降级、限流、故障隔离、备份恢复。
G. 安全与合规：用户隐私保护、数据传输与存储加密、防刷、API 鉴权、敏感数据脱敏。
H. 部署与运维：容器化/K8s/Serverless 选择、CI/CD、监控告警、日志链路追踪、压测方案。
I. 风险与取舍：列出 3-5 个关键架构取舍及回退方案。

【输出格式】
按「输出模板 - 完整架构方案」的章节输出，使用 Markdown 表格、架构图（ASCII 或 Mermaid）、SQL 代码块。

【评估标准】
- 方案是否能在 {{TARGET_QPS}} QPS 下保持 P95 < 500ms？
- 是否能在后端仅 2 人的情况下落地？
- 出分日流量突增 10 倍时系统能否自动扩容且不失效？
- 数据一致性是否满足志愿填报的准确性要求？
```

## 四、分阶段提示词（Phase Prompts）

### 阶段 1：业务场景与流量模型分析
```text
基于项目上下文，请先完成业务场景与流量模型分析，为后续架构设计提供量化输入。

{{粘贴项目上下文}}

任务：
1. 识别核心用例与调用链路（考生登录→填写成绩→设置偏好→获取推荐→查看志愿表→导出/保存）。
2. 估算各链路在日常、出分日、峰值时刻的 QPS、RT、数据量。
3. 定义关键性能指标：推荐接口 P50/P95/P99、并发用户数、同时在线会话数。
4. 识别热点数据（如热门院校、热门专业、各省分数线表）与热点操作（如批量推荐）。
5. 输出流量模型表格与架构设计假设清单。

约束：
- 峰值 QPS 目标 {{TARGET_QPS}}。
- 推荐接口 P95 必须 < 500ms。
- 需区分读多写少的数据特征。
```

### 阶段 2：架构模式与服务拆分
```text
基于阶段 1 的流量模型，为高考志愿填报 APP 设计顶层架构模式与服务拆分。

{{粘贴项目上下文}}
{{粘贴阶段 1 输出}}

任务：
1. 选择架构模式：单体/模块化单体/微服务/Serverless/混合，并说明理由。
2. 按业务边界拆分服务，绘制服务拓扑图（Mermaid）。
3. 每个服务给出：职责、依赖关系、数据 ownership、对外暴露接口类型（REST/gRPC/事件）。
4. 说明 API Gateway / BFF 层的设计（鉴权、限流、路由、协议转换）。
5. 明确团队 2 人后端的运维负担，优先推荐托管服务或成熟云组件。

约束：
- 服务数量不宜过多，避免 2 人团队无法运维。
- 推荐引擎必须独立可扩展。
- 数据服务按省/院校维度具备水平扩展能力。
```

### 阶段 3：数据架构设计
```text
基于已确定的服务拆分，设计数据持久化层。

{{粘贴项目上下文}}
{{粘贴阶段 2 输出}}

任务：
1. 核心实体建模：用户、考生档案、成绩、偏好、省份、院校、专业、招生计划、历年分数线、志愿表、推荐记录。
2. 为每个核心表提供 DDL（PostgreSQL/MySQL 语法），包含字段、主键、外键、CHECK 约束。
3. 索引设计：列出所有高频查询及对应索引（含复合索引、部分索引、GIN/GiST 等）。
4. 分片/分区策略：按省份、年份、批次分区，说明路由规则。
5. 读写分离与主从架构：写主库、读从库，推荐配置与延迟容忍。
6. 数据同步：静态基础数据（院校/分数线）如何导入、校验、版本控制。
7. 数据备份与归档策略。

约束：
- 院校/专业/分数线表为只读热数据，用户数据为写多读少。
- 必须保证位次、分数线等核心数据的准确性。
- 查询平均响应 < 100ms。
```

### 阶段 4：推荐引擎架构
```text
设计智能推荐引擎的完整技术实现方案。

{{粘贴项目上下文}}
{{粘贴阶段 3 输出}}

任务：
1. 推荐流程：输入（分数、位次、省份、科类、偏好）→ 候选生成 → 位次直查 → 线差校验 → 加权排序 → 输出。
2. 计算模式选择：预计算 vs 实时计算 vs 混合，说明触发条件与数据更新机制。
3. 候选集生成策略：如何根据位次快速缩小院校/专业范围（如 Bitmap、倒排索引、区间索引）。
4. 加权排序实现：3 年加权（0.4/0.35/0.25）与院校/地域/专业三角权重的计算方式。
5. 缓存设计：推荐结果是否可缓存？缓存键设计、失效策略、一致性保障。
6. 并发控制：同一用户多次推荐、多用户共享计算资源时的隔离与限流。
7. 降级方案：当推荐服务过载时，如何返回兜底结果（如基于位次的保底列表）。

约束：
- 单次推荐 P95 < 500ms，P99 < 1s。
- 推荐结果必须可解释（返回匹配依据：位次、线差、概率等）。
- 支持零偏好模式与完整偏好模式两种输入。
```

### 阶段 5：缓存与性能优化策略
```text
为整个后端设计多级缓存与性能优化方案。

{{粘贴项目上下文}}
{{粘贴阶段 4 输出}}

任务：
1. 缓存分层：CDN（静态资源）→ 边缘缓存 → API Gateway 缓存 → 应用本地缓存（Caffeine/Guava）→ Redis 缓存 → 数据库。
2. 热点数据识别：院校基础信息、专业列表、各省分数线、招生计划、位次段映射。
3. 缓存一致性：数据库更新后如何失效/刷新缓存，防止脏读与缓存击穿。
4. 本地缓存 vs 分布式缓存：哪些数据适合本地缓存，哪些必须 Redis。
5. 异步加载与预热：考季前如何全量预热缓存，出分日如何动态补热。
6. 连接池、线程池、NIO、批处理、查询合并等代码层优化建议。
7. 压测与性能基线：关键接口基准数据与优化前后对比。

约束：
- 缓存命中率目标 ≥ 95%。
- 不能因为缓存导致推荐结果与用户实际输入不一致。
- 数据库 CPU 使用率峰值 < 70%。
```

### 阶段 6：高可用与容灾
```text
设计系统的高可用架构与容灾方案，确保出分日稳定运行。

{{粘贴项目上下文}}
{{粘贴阶段 5 输出}}

任务：
1. 多可用区/多Region部署：哪些服务需要跨 AZ，哪些可以单 AZ。
2. 数据库高可用：主从复制、自动故障转移、读写分离、延迟监控。
3. 服务层高可用：无状态化、健康检查、自动重启、滚动发布、灰度发布。
4. 限流与熔断：接口级限流（用户/全局）、服务级熔断、降级策略。
5. 故障隔离：按省份/用户分片隔离，避免单点故障扩散。
6. 容灾演练：数据备份恢复演练、主从切换演练、全链路压测。
7. RTO/RPO 目标定义。

约束：
- SLA ≥ 99.9%。
- 单点组件故障 30 秒内自动恢复或降级。
- 数据库主从切换数据丢失为 0（同步复制）或容忍 <5 秒（异步复制需说明）。
```

### 阶段 7：安全与合规
```text
设计系统的安全与合规框架。

{{粘贴项目上下文}}
{{粘贴阶段 6 输出}}

任务：
1. 身份认证：考生登录方案（手机号验证码、微信 OAuth、Token 机制）。
2. 权限控制：用户只能访问自己的成绩与志愿表，防止越权。
3. 数据传输安全：TLS 1.3、证书管理、HSTS。
4. 数据存储安全：密码/Token 加密、PII 脱敏、数据库加密（TDE）。
5. 防攻击：DDoS、CC、SQL 注入、XSS、CSRF、暴力破解、刷接口。
6. 防刷限流：短信验证码限流、推荐接口限流、IP/设备指纹风控。
7. 合规：个人信息保护法、未成年人数据保护、数据最小化原则。
8. 安全审计：操作日志、敏感操作告警。

约束：
- 考生身份证号、手机号必须加密存储且脱敏展示。
- 关键接口（成绩提交、推荐生成）必须有审计日志。
- 不得因安全措施使推荐接口 RT 增加超过 20ms。
```

### 阶段 8：部署、监控与成本

```text
{{粘贴项目上下文}}
{{粘贴阶段 7 输出}}
```

## 五、专项提示词（Specialized Prompts）

### 专项 1：API 设计规范
```text
为高考志愿填报 APP 设计一套 RESTful API 规范。

要求：
1. 覆盖核心接口：用户注册/登录、考生档案、成绩录入、偏好设置、获取推荐、志愿表 CRUD、导出志愿表。
2. 统一响应格式：{ "code": 0, "data": {}, "message": "", "traceId": "" }。
3. 错误码设计：按模块分层（用户 1xxx、成绩 2xxx、推荐 3xxx、系统 9xxx）。
4. 分页、过滤、排序规范。
5. 接口幂等性设计（成绩提交、志愿保存）。
6. 版本控制策略。
7. 给出每个接口的 OpenAPI 3.0 示例片段。
```

### 专项 2：数据库索引与查询优化
```text
针对高考志愿填报 APP 的核心查询场景，做数据库索引与查询优化专项设计。

场景：
1. 根据省份+科类+年份+位次范围查询可填报院校专业。
2. 根据院校 ID 查询历年录取分数/位次。
3. 根据用户 ID 查询考生成绩与志愿表。
4. 根据省份+批次查询招生计划。
5. 推荐引擎内部的多表 JOIN/聚合。

要求：
1. 为每个场景给出最优索引方案（含 SQL DDL）。
2. 给出执行计划分析（EXPLAIN）要点。
3. 说明如何避免全表扫描、索引失效、深分页问题。
4. 对极热查询给出 Redis/本地缓存优化方案。
```

### 专项 3：压测与容量规划
```text
为高考志愿填报 APP 设计压测方案与容量规划。

要求：
1. 压测目标：推荐接口、院校查询接口、成绩提交接口。
2. 压测工具与脚本框架（如 k6、JMeter、Locust）。
3. 场景模型：日常、出分日、极端峰值。
4. 数据构造：模拟考生、模拟位次分布、模拟偏好组合。
5. 监控指标：QPS、RT、错误率、CPU、内存、DB 连接、缓存命中率、GC。
6. 容量规划：根据压测结果推导日常/峰值所需节点数。
7. 给出扩容触发条件与回滚条件。
```

### 专项 4：缓存一致性方案
```text
针对高考志愿填报 APP，设计缓存一致性保障方案。

要求：
1. 明确哪些数据入缓存（院校信息、分数线、招生计划、推荐结果、用户会话等）。
2. 缓存更新策略：Cache-Aside、Write-Through、Write-Behind 的选择与适用场景。
3. 缓存失效策略：TTL、主动失效、版本号机制。
4. 防止缓存击穿、穿透、雪崩的具体措施。
5. 推荐结果缓存键设计（如何平衡命中率与结果准确性）。
6. 数据库与缓存不一致时的兜底与补偿机制。
```

### 专项 5：技术选型对比
```text
针对以下关键技术点做选型对比，给出推荐方案与理由。

对比项：
1. 数据库：PostgreSQL vs MySQL vs TiDB
2. 缓存：Redis Cluster vs Redis Sentinel vs 云托管 Redis
3. 消息队列：是否需要？Kafka/RabbitMQ/RocketMQ 选型
4. 推荐计算：应用内实时计算 vs 独立 Python/Go 服务 vs 预计算表
5. 部署：K8s vs Serverless vs 传统 ECS
6. API 协议：REST vs gRPC vs GraphQL

输出格式：
- 每个对比项用表格列出优缺点、适用场景、推荐选型、回退方案。
- 综合考虑团队规模 2 人后端的落地成本。
```

## 七、评估 Checklist

### 7.1 性能评估
- [ ] 推荐接口 P95 < 500ms（含网络往返）
- [ ] 院校/专业查询 P95 < 200ms
- [ ] 数据库查询平均 RT < 100ms
- [ ] 缓存命中率 ≥ 95%
- [ ] 支持峰值 QPS ≥ {{TARGET_QPS}}
- [ ] 出分日流量突增 10 倍时仍满足 RT 要求

### 7.2 高可用评估
- [ ] SLA ≥ 99.9%
- [ ] 单点故障有自动转移或降级
- [ ] 数据库主从切换 RTO < 60s
- [ ] 限流/熔断策略覆盖所有核心接口
- [ ] 有完善的监控告警与 on-call 流程
- [ ] 发布支持灰度/回滚

### 7.3 可落地性评估
- [ ] 后端 2 人团队可开发与运维
- [ ] 优先使用托管服务/成熟组件
- [ ] 技术栈与团队能力匹配
- [ ] 10 周核心开发周期内可完成 MVP
- [ ] 成本在 {{BUDGET_LEVEL}} 范围内

### 7.4 安全与合规评估
- [ ] 考生敏感信息加密存储
- [ ] 关键接口有审计日志
- [ ] 防刷/限流/风控机制完整
- [ ] 符合个人信息保护法要求
- [ ] 越权访问被有效阻止

### 7.5 数据准确性评估
- [ ] 院校/专业/分数线数据来源可靠
- [ ] 数据导入有校验与版本控制
- [ ] 推荐结果可解释、可追溯
- [ ] 缓存不会导致推荐结果与数据库不一致
