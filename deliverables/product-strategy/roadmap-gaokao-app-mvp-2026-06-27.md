# 高考志愿填报APP MVP — 路线图与里程碑规划

**版本**：V1.0
**日期**：2026-06-27
**类型**：路线图 / 时间线规划
**参与成员**：路径（路线图规划师）、析客（需求分析师）

---

## 📌 TL;DR（执行摘要）

本路线图将PRD中6个里程碑从串行12.5周压缩至并行10周核心开发周期，并覆盖从项目启动到2027高考出分日上线的完整12个月生命周期。关键策略：**数据先行+算法与前端并行+对话式入口降级弹性**。最硬性约束是出分日（2027年6月23日）前必须上线，且一分一段表24h入库是运营级红线。建议7月中旬启动开发，9月底完成核心开发，10月至次年5月为长周期测试与数据验证窗口。

## 2. 关键依赖关系

### 2.1 依赖关系图

```
M1-数据基础 ──────┬────→ M2-采集引擎 ──────┬────→ M3-推荐引擎 ──────→ M4-推荐展示
    (W1-W2)        │       (W3-W5)           │       (W4-W7并行)        (W6-W8并行)
                   │                          │
                   │                          ├────→ M5-对话式入口
                   │                          │       (W8-W9.5)
                   │                          │
                   └──────────────────────────┴────→ M6-联调测试
                                                      (W9.5-W10)

外部决策依赖：
  Q-1(数据采购) ──→ M1（阻塞级）
  Q-4(Top10省排序) ──→ M1+M2（阻塞级）
  Q-3(AI模型选型) ──→ M5（阻塞级，M5可降级）
  Q-2(数据更新频率) ──→ M1架构设计（非阻塞）
  Q-5(加分规则数据) ──→ M2加分处理（非阻塞）
  Q-6/Q-7/Q-8 ──→ M3/M4细节（可开发中迭代）
```

### 2.2 串行 vs 并行策略说明

**可并行的工作流**：

| 并行组 | 并行内容 | 并行条件 | 压缩效果 |
|--------|---------|---------|---------|
| **并行组A** | M3算法设计 + M2前端开发 | M3算法团队在M2期间用Mock用户画像数据先行开发核心逻辑，仅最后1周对接真实数据模型 | 压缩2周（M3从W5启动提前至W4） |
| **并行组B** | M4前端开发 + M3尾部开发 | M4前端基于API契约先行开发展示页，M3完成后对接真实API | 压缩1.5周（M4从W7启动提前至W6） |
| **并行组C** | M5对话式 + M4尾部 | M5后端在M4期间先行开发NLP解析+数据映射，前端与M4并行 | 压缩0.5周 |

**必须串行的工作**：

| 串行约束 | 原因 |
|----------|------|
| M1 → M2位次反查 | 位次反查API依赖一分一段表数据 |
| M2数据模型 → M3真实对接 | 推荐引擎最终对接需要真实user_profile数据模型 |
| M3推荐API → M4真实对接 | 结果页需要真实推荐数据才能完成交互调试 |
| M1-M5全部 → M6联调 | 联调必须所有模块就绪 |

**总压缩效果**：串行12.5周 → 并行10周，节省2.5周。
