# 高考志愿填报APP · 业务场景与流量模型分析 v1.0

> 为后续后端架构设计提供量化输入。基于 MVP 覆盖 Top10 省、后端 2 人团队、峰值 QPS ≥ 10,000 的目标进行估算。

---

## 1. 分析范围与基础假设

### 1.1 覆盖范围
MVP 覆盖 Top10 省：广东、河南、山东、江苏、四川、河北、湖南、安徽、湖北、浙江。

### 1.2 用户规模假设

| 指标 | 数值 | 说明 |
|------|------|------|
| Top10 省考生总数 | ~600 万 | 2026 年预估 |
| APP 目标渗透率 | 5% | MVP 阶段 |
| 注册用户总数 | 30 万 | 600 万 × 5% |
| 出分日活跃用户 | 24 万 | 注册用户的 80% |
| 出分日峰值同时在线 | 12 万 | 活跃用户的 50% |
| 人均推荐次数 | 4 次 | 含多次调整偏好后重新推荐 |
| 人均查询次数 | 20 次 | 院校/专业/分数线浏览 |

### 1.3 时间分布假设
- **日常**：考季前 1-2 个月有少量用户提前了解院校信息，流量平稳。
- **出分日**：高考出分后 24-72 小时内流量爆发，峰值集中在出分后 2-4 小时。
- **峰值小时**：假设 60% 的推荐请求和 40% 的查询请求集中在出分后前 2 小时。

## 2. 核心用例与调用链路

### 2.1 核心用例图

```mermaid
graph LR
    A[考生] --> B[注册/登录]
    B --> C[填写考生档案]
    C --> D[录入成绩与位次]
    D --> E[设置偏好]
    E --> F[获取智能推荐]
    F --> G[查看院校/专业详情]
    G --> H[收藏/对比志愿]
    H --> I[生成志愿表]
    I --> J[导出/保存志愿表]
```

### 2.2 关键调用链路

#### 链路 1：登录 → 获取推荐（主链路）
```
登录 → 获取考生档案 → 获取最新成绩 → 获取偏好 → 调用推荐引擎 → 返回推荐结果
```
- 涉及接口：登录、GET /candidate、GET /score、GET /preference、POST /recommend
- 关键路径：推荐引擎计算

#### 链路 2：浏览院校/专业详情（高频读链路）
```
搜索院校 → 获取院校列表 → 获取院校详情 → 获取专业详情 → 获取历年分数线
```
- 涉及接口：GET /universities、GET /universities/{id}、GET /majors、GET /admission-scores
- 特征：读多写少，强依赖缓存

#### 链路 3：保存/导出志愿表（低频写链路）
```
创建志愿表 → 添加志愿项 → 保存 → 导出 PDF
```
- 涉及接口：POST /wishlists、PUT /wishlists/{id}、POST /wishlists/{id}/export
- 特征：写操作，数据一致性要求高

## 5. 热点数据与热点操作识别

### 5.1 热点数据

| 数据类型 | 热度 | 访问特征 | 缓存策略 |
|----------|------|----------|----------|
| 热门院校基础信息 | 🔥🔥🔥 | 清北复交等 985/211 院校详情被高频访问 | 本地缓存 + Redis + CDN |
| 热门专业信息 | 🔥🔥🔥 | 计算机、临床医学、金融等热门专业 | Redis + 本地缓存 |
| 各省分数线表 | 🔥🔥🔥 | 出分后全省考生都会查询本省数据 | Redis 全量缓存 |
| 招生计划 | 🔥🔥🔥 | 本省所有考生都会查询 | Redis 全量缓存 |
| 位次区间映射表 | 🔥🔥🔥 | 推荐引擎核心依赖，每次推荐必查 | 推荐引擎本地内存 + Redis |
| 用户成绩 | 🔥🔥 | 单用户私有，但写入集中 | Redis 会话级缓存 |
| 推荐结果 | 🔥🔥 | 同成绩+同偏好可复用 | Redis 30min TTL |
| 志愿表 | 🔥 | 用户私有，写入低频 | 数据库 + 短缓存 |

### 5.2 热点操作

| 操作 | 热度 | 场景 | 风险 | 应对策略 |
|------|------|------|------|----------|
| 获取推荐 | 🔥🔥🔥 | 出分后几乎所有用户都会触发 | 推荐引擎过载 | 预计算 + 本地缓存 + 限流 + 熔断降级 |
| 院校/专业搜索 | 🔥🔥🔥 | 浏览阶段高频 | 数据库读压力 | Redis 全量缓存 + 搜索引擎/全文索引 |
| 分数线查询 | 🔥🔥🔥 | 决策参考必查 | 缓存击穿 | 预热 + 请求合并 + 降级 |
| 成绩录入 | 🔥🔥 | 出分后 2 小时内集中 | 写库压力 | 异步写 + 队列削峰 |
| 短信验证码登录 | 🔥🔥 | 登录高峰 | 短信通道/费用 | 限流 + 图形验证码 + 多渠道 |
| 保存志愿表 | 🔥 | 最终决策时 | 数据一致性 | 主库写入 + 幂等设计 |
| 导出志愿表 PDF | 🔥 | 最终阶段 | 计算/IO 开销 | 异步生成 + 缓存结果 |

## 8. 对后续架构设计的输入

### 8.1 关键量化结论
1. **读多写少**：出分日读请求占比 > 90%，缓存是核心优化手段。
2. **查询流量是推荐的 7-8 倍**：院校/专业/分数线查询是绝对大头，需重点优化读缓存。
3. **省份天然隔离**：可按省份分片部署或分区，降低单点风险。
4. **峰值需预留 50% 缓冲**：设计容量应按 15,000 QPS 考虑。
5. **推荐是计算瓶颈**：推荐引擎必须独立、可水平扩展、支持本地缓存。

### 8.2 架构设计重点
1. **缓存优先**：Redis 全量缓存本省基础数据，推荐引擎本地内存缓存位次映射表。
2. **读写分离**：写操作走主库，查询和推荐读只读副本。
3. **推荐引擎独立**：作为独立服务，可按省份或按流量单独扩缩容。
4. **限流降级**：推荐接口限流 10 次/分钟/用户，过载时返回兜底列表。
5. **预热机制**：考季前将 Top10 省数据预热到 Redis 和推荐引擎内存。
6. **按省分片**：数据按省份分区，服务可按省份灰度发布和故障隔离。

### 8.3 待验证假设
- 实际用户渗透率可能高于或低于 5%，需在考季前根据注册量修正。
- 各省出分时间不同，峰值不会完全叠加，但同一省份内峰值极高。
- 推荐算法复杂度可能影响 RT，需在实现后做基准压测验证。
